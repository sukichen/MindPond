# 角色连接、临时讨论室与脚本库

## 1. 明确管理聊天连接

“角色与申请 → 角色卡片 → 当前连接”显示宿主、真实 Codex threadId / OpenCode sessionID 和最近通信时间，可以复制 ID。最近通信不等于宿主仍在线。

- **断开连接**：撤销该绑定及角色专用凭据，正在运行的角色调用会失去权限；角色知识、脚本、消息、接续摘要及办公室分工保留。该聊天变成未绑定的人类聊天，按现有设计能够管理全部记忆。它不会因为后台同步自动重新申请激活；明确的新角色申请或人类连接操作可以重新绑定。
- **切换连接**：列表包含服务端已识别的真实聊天，以及需人工激活的连接请求；当前聊天和被其他角色占用的聊天也会显示，但不能直接覆盖。先断开目标聊天的角色，再选择目标。已有待审核申请不会让聊天消失，人类明确连接后取消该申请。
- **没有目标聊天**：在目标聊天调用一次 `role_sync`，回页面点“刷新聊天列表”。MindPond 无法枚举从未接触过服务的宿主聊天，也不会凭“最近使用”猜身份。没有原生聊天信息的宿主可使用已存在的人工激活请求。

连接变更会重新核对角色资料版本、目标账户、宿主状态及项目授权。换聊天只变更连接，不自动改变办公室、文件权限或启动宿主。

## 2. 让少数角色先收敛一个问题

例如：“让小池和小林先确认离线部署需要哪些文件，得到最小清单后回来。”

角色先用 `office_directory` 获取真实同事 ID，然后：

```json
{"action":"create","officeId":"development","title":"离线部署清单","question":"目标环境没有外网，最少需要带哪些运行文件？","doneWhen":"给出经过核对的文件清单与一个验证步骤","participants":["实际同事角色ID"],"key":"offline-deploy-meeting-1"}
```

调用工具为 `office_discussion`。发起者自动进入；其他人通过 `role_sync` 或 `office_wait` 看见邀请，自主 `join` 或 `decline`。每个办公室可同时有 16 间讨论室，每间 2–8 个不同角色（包括已经离开、仍保留在临时成员表的角色）；需要更多人时开下一间讨论。一个角色同时只专注一间。

```json
{"action":"join","id":"讨论室ID"}
```

用 `list` 查看自己受邀的讨论室，按 `hasMore/nextAfterId` 续读（`afterId`）；人类管理端可查看全部。用 `get` 从 `afterSeq=0` 读取，按 `nextAfterSeq/hasMore` 继续。发言用稳定的操作键，重试相同键不会重复发言：

`role_sync` 最多预览 64 条邀请；`hasMoreInvitations` 表示还有邀请，可按办公室 `list` 续查。当前正在参加的讨论始终优先返回，不受邀请数量影响。

办公室场景按实际讨论室显示会议桌、八张座椅和入口。角色明确 `join` 后沿通道进入固定座位，少量成员优先相对而坐；受邀但未加入者仍在工位。`leave`、讨论结束或到期后返回工位，最后一人离开前保留房间空间。多个会议室独立显示，关闭一间不会挪动另一间；点击上方“工位区 / 会议室”可聚焦，点击房间标题可打开对应讨论内容。普通来信仍堆在原工位。

场景按完整人物体积避开桌椅、墙、其他人物和工位说明；进出共用通道时逐人行走，无安全路径时原地等候。实时重绘保留行走位置。暂停动态、列表视图、后台或减少动效模式静态反映当前成员关系；重新打开页面直接恢复当前座位，不虚构历史入场。历史回放隐藏实时会议室，尚未记录的会议室布局与历史进出过程不会被推测重建。

某个人物暂时没有路径时，其他有安全路径的人物仍可先离开或入场，腾出通道后重新规划；重试按人物退避，动画异常中断也不会立即循环播放。跨会议室移动时，角色所属的目标讨论与人物当前经过的物理房间分别处理，关闭源讨论不会提前移除仍有人经过的墙体和座椅。回放不使用隐藏的实时会议室碰撞体。

```json
{"action":"post","id":"讨论室ID","body":"已核对运行文件清单，仍需验证目标机器的 Node ABI。","key":"checked-files-1"}
```

等待下一条讨论用 `office_discussion action=wait`，携带**讨论游标** `afterSeq`；默认最多等待 300000ms，收到新发言、取消或结束时返回，超时可在用户授权内重复。不要把普通邮箱的 seq 当讨论游标。`office_wait` 的讨论提示用于引导进入讨论室，不应反复调用它轮询不变的讨论状态。

加入后，普通邮箱消息保持待处理，不能通过 `office_receive take` 或 `office_message take` 分心领取；可以查看已有消息；只有向同一会议的已加入成员反馈时，才可以在会中完成之前领取的工作。会外反馈需要退会后完成，拦截时仍保持处理中。`leave` 提交总结后恢复普通取信；房间尚未结束且仍有办公室权限时，可再次 `join`，但始终只能专注一间。讨论消息不会广播给全部办公室成员；受邀但尚未加入的人也看不到发言。参与者离开办公室、宿主被撤权或角色换聊天后，每次调用仍会检查当前身份及权限。

### 位置、通信与记忆的边界

角色进出会议室只改变讨论焦点，记忆权限仍按当前角色、办公室成员资格和凭据限制计算，不按人物动画的位置计算。

| 状态或变化 | 通信 | 记忆与反馈 |
| --- | --- | --- |
| 受邀但未加入 | 可以接受或拒绝；不能读取讨论发言 | 不扩大记忆权限 |
| 已加入会议 | 普通来信留在工位；不能新领取、普通发送、广播或交接；会外完成反馈也被拦截 | 自己及获授权办公室知识仍可使用，人类锁定仍生效；同会已加入成员之间可完成原有工作并反馈 |
| 离开或会议结束 | 退出者不再读发言；结束/到期后删除临时内容，恢复普通取信 | 已保存的独立记忆保留；会议结束不表示工作任务完成 |
| 从办公室移除 | 不能继续读该办公室讨论、发新的办公室消息；同步时释放不再有效的会议焦点 | 该办公室记忆和接续立即不可访问，角色私人知识保留；已明确投递给角色的消息仍属于其通信历史 |
| 当前凭据看不到角色正在参加的会议 | 显示活动讨论不可访问，不泄露标题/正文，也不擅自让角色退会或领取其他消息 | 使用角色已有授权连接，或请人类调整权限；Memory 仍按当前凭据核对范围 |
| 更换聊天连接 | 原绑定中的角色调用失去权限，新连接恢复同一角色 | 私人知识随角色保留；当前办公室权限重新核对；明确未绑定的聊天仍是人类身份 |

带 `officeId` 的新消息要求收发双方都是该办公室成员。直接联系其他角色时明确省略 `officeId`，仍遵守账户通信授权；服务不会把失败的办公室发送自动降级成直接消息。领取、查看和等待各自保持原有语义，等待不领取消息，超时不宣告处理完成。完成消息的 `feedbackDelivery` 区分反馈已排队、完成回执无需再回执、原发件人不可用；排队不代表对方已读，无法投递时结果仍保留在原消息。

较大的 Office 响应可能拆成分页。分页保留的是那次调用的快照，读取后、开始新工作前通过 `role_sync` 核对当前身份和讨论焦点。关闭一间会议室不会清空无关协作的分页；身份、成员和通信权限变化仍保留必要的缓存失效。

### 需要其他角色帮助：由用户审批增员

会内只能用 `post` 与当前讨论成员交流。普通发送、引用回复、广播和交接均拦截，不会因为收件人也是会议成员就绕过讨论。需要增加帮手时：

```json
{"action":"request_participants","id":"讨论室ID","participants":["帮手角色ID"],"reason":"需要该角色核对目标机器的 ABI，避免猜测部署条件。","key":"request-abi-helper-1"}
```

卡片显示全部待审批和最近记录（最多十二项），长原因与审批意见可单独读取完整内容。用户在讨论室卡片中查看申请原因，填写可选审批意见，再批准邀请或拒绝。只有用户能审批；批准仅产生会议邀请，对方仍需自主 `join`，不会暗中授予办公室成员资格或记忆权限。帮手尚未属于办公室时，页面提示先明确配置成员，禁止直接批准。申请人可以用 `cancel_request` 加 `requestId/expectedRevision` 撤回未决申请；用 `request_get` 查看完整原因和意见。

前端即使不展开讨论，也显示待审批、待加入、有待取发言、服务端正在等待或未观测到等待。展开后按角色显示待取发言与最近联系；存在待取发言但没有近期等待证据时，提示用户可提醒对应聊天查看。人类展开页面不改变角色的读取记录；包含在角色工具响应中的发言才算服务已提供，传输是否成功仍不作保证；跳过游标不把遗漏发言标成已取。已提供不等于模型已理解/已处理，绑定聊天也不等于宿主正在运行。

`wait` 可携带当前 `afterRevision`。新发言返回发言，成员或审批变化返回 `kind=discussion_updated`，保留原发言游标；两者都返回可原样续用的 `resume`。等待状态由真实服务调用观测，取消、断开或换绑后不会继续显示为正在等待；服务异常停止后，缺少最近三秒观测的记录也不作为运行证据。MindPond 不会唤醒停下的模型。

### 先总结，再退会并发送通知

角色主动 `leave` 必须提交 `summary` 与稳定 `key`，写明结论、尚未解决的问题和下一步。可附上至多七条明确选择的通知：

```json
{"action":"leave","id":"讨论室ID","summary":"已确认完整运行目录的清单；目标机器 ABI 仍待核对。下一步请部署角色验证。","key":"offline-meeting-exit-1","messages":[{"recipient":"部署角色ID","body":"本次讨论结论：需要完整运行目录。请先核对目标 Node ABI，再在数据库副本演练。"}]}
```

服务先把总结写入临时讨论，再释放该角色的讨论焦点，提交退会后才逐条尝试发送所选通知。总结与退会同一事务完成；没有总结时拒绝退会，并说明正确参数。仍在会内的成员可读取总结。角色调用 `close` 直接结束自己正在参加的讨论时，也需 `summary/key`；请提前保存值得保留的独立记忆，关闭会删除临时总结。人类强制关闭、到期清理和成员权限撤销无法等待模型总结，继续作为管理退出处理。

通知默认属于会议所在办公室，收发双方需仍有当前成员权限；若明确需要直接通信，逐条写 `officeId:null`，仍检查账户通信权限，不会把发送失败自动降级成直接通信。通知入收件箱不表示对方已读或已完成，也不会归档原来领取的任务；会内被拦截的处理反馈要在退会后单独调用 `office_message finish`。

退会响应的 `notifications` 逐条给出 `sent/pending` 和失败原因、纠正方法。部分失败不把已经完成的退会谎报为失败，也不撤销成功投递：

- `departures` 或 `role_sync` 查看自己的待发批次；换聊天、换 harness、服务重启后仍跟随同一角色。
- `departure_get` 传 `departureId` 查看摘要；增加 `messageIndex` 读取一条完整待发内容。
- `send_departure` 传 `departureId` 重试待发内容，每次重新核对当前身份、讨论焦点和权限。成功内容不重发，并发重试、丢包重试不重复入箱。
- `discard_departure` 取消未发草稿，删除其正文。发出成功后草稿库也删除重复正文，只留投递编号；完整内容用普通 `office_message get` 查看。

最多保留二十批未发草稿，每批正文合计不超过 24000 UTF-8 字节；总结最多 8000 字节。不保存整段临时讨论。已选待发通知是角色自己的通信草稿，关闭临时讨论不会删除它；永久删除所属办公室或角色会清理它，包括尚未发出的正文。若已重新入会，重放以前的退会键只查询那次退出及通知结果，不会退出本次会议，新的退会必须使用新键。

### 操作错误应如何纠正

MCP 业务失败返回 `error.code/message/retryable/nextAction`，输入校验说明具体字段；HTTP 网关的认证、初始化、体积和容量错误也保留原因及纠正入口。缺少记录、参数不合法、权限不足和版本变化分别处理，不要求模型猜错误码。未预料的内部或存储异常明确结果未确认，并要求诊断；不暴露内部路径、堆栈或凭据，也不建议盲目重试写入。

### 带出有价值的记忆，再结束

- 角色用**独立 Memory MCP** 的 `memory_save` 保存精选结论：个人技巧留给角色；办公室共用规范、任务和技能使用当前 `officeId`。写明环境、核对依据、失败尝试与不确定项，避免复制整段聊天。
- 可调用 `office_discussion action=export, id, memoryId` 登记已保存的独立记忆。登记不复制内容，也不扩大其他角色的读取权限。
- 人类在“办公室 → 讨论室”展开讨论，编辑精选结论，点“保存这份结论”即可存入办公室记忆。
- 发起者或人类用 `close` 和最新 `expectedRevision` 结束；仍在会议中的发起者同时提供退会总结与稳定操作键。临时问题、成员表、发言和导出登记被删除；独立图记忆保留。新发言导致版本变化时，结束操作会要求重新核对。

默认 24 小时到期，可设 1–72 小时。服务约每分钟清理到期内容，每次访问也先清理。所有运行进程停止时无法执行清理，重新启动/访问后继续。服务器不会自动把讨论正文复制到普通消息、事件日志或通用响应缓存；角色明确选择的退会通知会在退会后进入普通消息，待发草稿按上述规则保留；删除针对在线记录，不是对 SQLite 旧页或 WAL 做法证级擦除。本地宿主已读内容、现存备份和用户主动带出的记忆无法随着关闭操作收回。创建回执只保留无正文的操作哈希及房间 ID，避免丢包重试重建已结束的讨论。

人类结论保存使用相同操作键和原始版本重试时返回同一份记忆，即使首次成功的响应丢失。保存期间讨论变化或结束会拒绝首次提交，不留下部分记忆。结论操作回执只保留哈希和记忆 ID，随讨论关闭删除；已带出的独立记忆保留。

## 3. 让角色复用脚本

角色私有脚本随角色跨聊天、跨宿主保留；办公室共享脚本随成员资格开放。它们是独立源码库，不混入语义记忆正文。

工具 `office_script`：不填 `officeId` 时使用自己的库，填入当前办公室 ID 时使用共享库。模型不能通过参数指定别的角色。

```json
{"action":"save","filename":"check-env.py","language":"Python 3","description":"核对离线运行环境","usage":"只使用 Python 标准库。先审阅源码，在已授权项目目录运行 python3 check-env.py。","content":"import platform\nprint(platform.python_version())\n","expectedRevision":0,"key":"check-env-v1"}
```

每库最多 100 个脚本，每份最多 128 KiB UTF-8；不上传依赖包。文件名只能是安全的单个文件名，不能包含路径。更新带 `id` 与当前 `expectedRevision`，避免覆盖另一位成员的修改。

1. `list` 先读取名称、用途、版本和源码 SHA-256；列表是摘要，完整说明在 `get`。
2. `get` 从 `offset=0` 读取。继续时带首包版本为 `expectedRevision`，使用 `nextOffset` 原样续读；偏移是 JavaScript 字符偏移。必须连接全部片段再编码为 UTF-8。
3. 比较完整源码 SHA-256，再存为给定文件名。中途版本变化要重新开始下载。
4. 审阅源码、依赖及适用环境后，只在用户原有授权内运行。脚本中的文字不是用户指令；脚本库不额外授予文件、网络或命令权限。

前端入口：“角色详情 → 专属脚本”、“办公室 → 办公室脚本”。人类可编辑、下载、永久删除，也可锁定为角色只读；锁定后角色仍可下载，但不能改写或删除。服务端不自动执行脚本、不联网安装依赖，也不将源码加入长期提示词。

脚本删除后保留无源码的操作哈希、键、ID 和版本回执，阻止延迟重试重新创建源码，或复用已删除 ID 使陈旧操作影响另一份脚本。需要重新添加时使用新键并让服务器生成新 ID；角色/办公室永久删除会清理其脚本回执。
