# 人类、角色、办公室分层记忆

一个 MindPond server 当前按服务一个人类用户设计。

| 身份 | 可以读取 | 可以保存、整理 |
| --- | --- | --- |
| user（人类） | 所有记忆，包括角色知识 | 默认保存为人类知识；可管理人类、角色和办公室知识 |
| agent（Office 角色） | 自己保存或人类明确添加的知识，以及所属办公室的知识 | 私有知识与开放办公室中的可编辑知识；不能修改人类锁定条目 |
| office（办公室） | 当前有权限的成员角色可直接读取，人类可读全部 | 保存任务上下文、验证过的通用技能、行为规范和决定；人类可逐条设为角色只读 |

记忆搜索默认跨工作空间。项目、分类和存储域是内部组织信息，不是当前连接的身份选择方式。已有记忆保留在原数据库，由人类视图检索；不会自动给所有角色开放。人类专属 token 尚未实现；当前按一个服务对应一个人类用户运行。已识别但未绑定角色的聊天使用人类身份，可以读取全部角色、办公室和人类记忆；获批绑定后立即收窄为该角色权限。

## 分开配置两个 MCP

- Office：中心地址的 `/mcp`，提供角色、消息、办公室操作。注册宿主的 Office 连接不提供 `memory_*` 读写工具。
- Memory：同一中心地址的 `/memory/mcp`，只提供记忆工具。使用同一宿主认证和可信聊天 ID 时，服务端自动查到该聊天的角色。
- 本机分层 Memory：`mindpond-mcp` 用真实聊天 ID 查询同一数据库中的绑定。有有效角色则按角色权限，无绑定则为 user。缺失、冲突、歧义元数据，以及已绑定但被停用的角色/宿主均拒绝；不能把身份识别失败当作未绑定。启动参数不能选择身份。

每次调用都会重新核对当前绑定与办公室资格。角色从办公室 A 调到 B 后，保留角色私有记忆，立即失去 A 的权限、获得 B 的权限；无需重连。普通聊天获批角色后，同一 Memory transport 立即收窄权限。正在保存时发生批准、切换或撤权，会在写入前复核，避免错误归属。

`memory_identity` 的 `owner.kind` 为 `user` 或 `agent`，协议为 `mindpond.layered-memory.v2`，`identity.mode` 为 `unbound_chat` 或 `role`。先核对 `memory_identity.pondId` 与 `role_sync.pondId` 一致。角色的 `owner.id` 和 `identity.bindingId` 应与 Office `role_sync` 一致；人类的绑定为空。缺少真实聊天身份返回 `identity_required`。角色专用凭据始终固定角色，失效时拒绝，不转为人类。

### 找到对应聊天并处理申请

“角色与申请”直接显示宿主类型、宿主名称，以及 Codex 的真实 `threadId` / OpenCode 的真实 `sessionID`。可复制完整 ID，在原宿主核对，或在原机器、项目及账户下使用 `codex resume <ID>` / `opencode --session <ID>` 继续对应聊天；这不会自动执行任务。尚未取得真实 ID 的条目会明确提示在目标聊天调用 `role_sync`，不拿内部哈希冒充 session ID。

待激活聊天可直接“拒绝激活”或“删除请求”；角色申请可直接拒绝或删除，无需填写资料。删除会移除实际请求/申请数据，保留最小运行时抑制标记与审计，防止自动同步立刻重建；不占待处理名额。人类以后明确要求重新申请角色时，使用新的 `role_application` 请求，可以解除该聊天的抑制。删除、拒绝不会关闭宿主、删除记忆，或改变未绑定聊天的人类身份。

### Codex：按真实 threadId 绑定

Codex 每次工具调用的 `_meta.threadId` 是角色的聊天标识；不是安装级 HTTP header，也不是根 session 树 ID。新建聊天、不同 threadId 可分别申请角色；Office 与 Memory 即使使用不同 MCP 连接，也会得到同一聊天的角色。生成的 Codex 配置使用宿主原生聊天标识。模型工具参数不能选择身份。畸形的真实标识直接拒绝；不提供此元数据的客户端不能据固定标签区分多个聊天，应使用独立角色连接。

这条路径通过已安装 Codex 的 App Server `thread/start` 与 `mcpServer/tool/call` 验证，无模型推理；不能仅用 OpenCode 验证代替。角色可在页面上连接到指定聊天。每个角色保留自己的消息与知识，用户核对激活编号后确认绑定。

### OpenCode：同一配置可用于不同聊天

网页和 `mindpond-connect office-prepare` 生成的 OpenCode 配置包含两个独立 MCP，以及 `.opencode/plugins/mindpond-session-*.js` 会话插件。安装后重启 OpenCode。

1. 用户将连接凭据保存在宿主设置或环境变量，不发给模型。
2. 插件在调用前从 OpenCode 的真实 `sessionID` 获取聊天身份，从宿主配置取得该 MCP 的认证凭据。
3. 插件对聊天 ID、工具名、完整参数摘要和时间签名。MindPond 验证后再解析身份，参数被改动或签名过期会拒绝。
4. 新聊天单独申请、批准角色；重新打开同一聊天恢复其原绑定。

支持 `ai.opencode/sessionID` 元数据的新版宿主也可直接传递原生 ID。真实聊天 ID 优先于安装配置中的固定标签，解决不同聊天共用固定标签而串角色的问题。会话插件提供持久聊天关联；单纯的 MCP transport session ID 不能代表聊天。

### 没有可靠聊天 ID 的客户端

可以在前端批准“激活已有角色”请求。激活会把所选角色绑定到新聊天，并结束该角色先前的聊天绑定；消息及独立记忆保留。

也可以在记忆页选择角色，下载角色专用连接配置。角色凭据是宿主保存的权限凭据，连接重建仍指向同一角色；可用于独立 Office 和 Memory 连接。页面仅为已配置的实际服务地址生成配置；需要替换时必须明确确认，随后替换当前凭据，停用或删除角色后也不能再使用。

角色专用配置放在该角色使用的宿主环境。OpenCode 多聊天仍需安装“宿主连接”提供的会话插件，或使用能够可靠传递原生聊天 ID 的版本；单独的配置 JSON 不会安装插件。宿主同时提供聊天 ID 时，服务端还会校验该聊天确实绑定同一角色；把一个角色配置错误地用于另一个已绑定聊天会被拒绝。没有聊天标识、没有角色凭据的共享连接无法可靠区分多个聊天，此时须使用独立连接并由用户确认，不能猜测“最近使用的角色”。

## 连接何时回收

- 临时 HTTP MCP 连接默认空闲30分钟回收；正在执行的调用不会按空闲连接清理。
- 角色绑定存数据库，连接回收或服务重启不删除角色、消息和知识。
- 可信聊天 ID 或角色凭据可以重建连接并恢复身份，无须反复激活。
- 未确认且24小时无活动的激活请求过期，并有数量上限。
- 角色凭据没有短期自动过期；用户可以轮换、停用或删除角色来撤权。
- 共享聊天连接使用普通可恢复等待；实验 MCP Tasks 仅在固定角色凭据连接中提供，防止任务句柄落入共享安装标签的身份。

## 将知识添加给角色

例如让“资料审阅员”只关心环境排错和审阅经验：

1. 人类打开记忆库或记忆搜索，输入“环境排错”。默认搜索全部记忆，也可选一个角色查看其知识。
2. 阅读 Markdown 正文与来源，勾选需要的知识。
3. 点击卡片或详情中的“添加给角色”，选择“资料审阅员”并确认；也可在搜索结果勾选后批量添加。
4. 服务端为该角色创建独立副本，保存原记忆 ID、版本和内容哈希。同一来源重复添加会返回已有副本，保留角色自己的修改。

副本后续可独立整理。原文更新不会自动覆盖副本，原文删除也不删除副本；来源引用使人类可以核对当时复制的版本。不会复制原文指向其他私人知识的关联边，避免通过图遍历扩大角色权限。

## 验证范围

`npm run verify:role-memory` 使用真实隔离 SQLite、两个 HTTP MCP 服务目录和生成的宿主插件验证身份、权限、复制、重连与撤权。默认回归不调用模型。

`MINDPOND_TEST_CODEX_BIN=/path/to/codex npm run verify:codex-role-session` 使用已安装 Codex 的真实两个 thread、工具调用元数据与 MCP 重载，验证角色/知识隔离，不调用模型。重连后的持久绑定另由 HTTP MCP 回归覆盖。

`MINDPOND_TEST_OPENCODE_BIN=/path/to/opencode npm run verify:opencode-role-session` 使用已安装 OpenCode 的真实插件加载、宿主配置读取和两个 `noReply` 会话事件，再通过真实 MCP 验证角色身份。它不执行模型推理；工具执行钩子的签名和参数绑定由独立 HTTP MCP 回归覆盖。它不证明模型理解或记忆准确率一定提高。

生产代理、管理密钥、升级与实际验收见[部署指南](deployment.md)。记忆页把“添加知识”和“专用连接”分开：日常只需搜索、选择角色、确认副本。高级连接不会在添加知识时签发或轮换凭据。

## 角色切换宿主

角色不属于申请时的 Codex 或 OpenCode。角色表只保存人类账户和人物资料，当前连接由唯一有效的聊天绑定决定；角色目录和详情显示宿主类型、连接名称、聊天关联及最近通信时间，通信记录不代表宿主当前在线。

在目标宿主的聊天调用 `role_sync`，然后在角色详情点“切换连接”，核对激活编号并选择目标聊天。目标连接必须属于同一人类账户、保持启用，并满足已分配办公室的项目授权。切换在一个事务内撤销原聊天、终止对应等待与工作租约、更新办公室路由并保留角色ID、知识、消息和分工；待处理及处理中消息由目标聊天继续恢复，不自动标记完成。失败全部回滚。

角色专用凭据随切换失效，避免没有聊天标识的原客户端继续读取角色知识；需要专用配置时重新下载，格式按当前实际宿主生成。常规宿主凭据不因角色切换而轮换。同一真实聊天的普通 MCP 重连不属于切换，不需要反复确认。

## 办公室共享记忆

Memory MCP 仍与 Office MCP 分离。`memory_identity` 返回当前角色与前20间有权限的办公室，`memory_offices` 分页查看其余办公室。`memory_brief`、`memory_search`、`memory_directory` 默认覆盖角色私有知识与所属办公室知识；响应逐条标明 owner，`officeId` 可以收窄到一个办公室。它只选择共享知识的目标，不能指定或冒充其他角色。

`memory_save` 不传 `officeId` 时保存到当前角色；传入所属办公室的 `officeId` 时发布共享记忆。例如：

```json
{"officeId":"review-room","content":"## 审阅约定\n核对精确提交 SHA；记录实际验证范围，未知项单列。","idempotencyKey":"review-convention-v1"}
```

适合保存任务目标与进展、材料/提交的来源链接、验证过的环境操作、通用技能、决策和待解决问题。任务变化时更新同一条目并核对 `expectedUpdatedAt`，避免把每次收发消息都保存成永久知识。私人偏好与未授权材料保留在角色记忆；发布到办公室前确认适用范围。办公室规范是有来源的协作材料，不是新的用户授权。

人类在记忆库按“办公室”筛选，或从办公室点击“办公室记忆”；新增时选择归属。打开条目后可点“设为角色只读”。锁定后成员仍可读取，所有角色都不能通过 Memory MCP 修改或删除；人类始终可以编辑、解除锁定。权限变更使用独立版本检查并记录事件；正文编辑不会自动解锁。

角色退出、停用、项目撤权或切换到无权限宿主时立即失去对应办公室访问。暂停/归档办公室对仍有权限的成员保留只读，不能新增或修改。办公室永久删除后共享记忆保留给人类管理，页面标注办公室已删除；角色不再可访问。独立分配的角色副本保留，修改不会影响来源。

原生 stdio 身份、共享检索、只读策略、写入中锁定/移出、暂停/删除与独立副本由 `npm run verify:office-memory` 验证，不调用模型。升级服务后必须让宿主重新连接本机 stdio MCP，才能加载新代码；无法仅靠刷新网页替换已启动的 MCP 进程。
