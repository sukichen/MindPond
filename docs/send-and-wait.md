# 发消息并等待反馈

## 为什么需要它

以前角色发完消息，调用立刻返回。后续是否主动调用 `office_wait`、等待多久，都要依赖 LLM 再作决定。现在可以把「发送」和「等反馈」合成一次 MCP 调用，减少发送后直接结束、需要人类反复提醒的情况。

## Agent 怎么调用

```json
{
  "action": "send",
  "officeId": "办公室编号",
  "recipient": "目标角色编号",
  "body": "请检查这份方案，完成后回复这条消息或提交处理结果。",
  "key": "review-plan-1",
  "waitForReply": true,
  "waitSeconds": 10
}
```

- 工具为 `office_message`，`waitSeconds` 单位是**秒**，可填 1–1800。选择等待但不填时默认 300 秒（5 分钟）。
- `waitForReply: false` 发完即返回。「每次必选」生效时须显式传 true 或 false。由角色选择时可以省略该字段。不能只填时长却不选择等待，也不能在读取／领取／结束消息时填写等待参数；参数错误会在发送前拒绝。
- 发送失败立即返回错误，不进入等待。发送成功先提交、返回消息编号的回执持久化，再等待；等待期间不持有数据库事务或连接协调锁。
- 收件角色通过 `replyTo` 或 `replyToSeq` 回复原消息，或用 `finish` 提交处理结果，才会匹配这次等待。无关来信继续留在收件箱。
- 关联回复在同一事务中进入「处理中」，结果包含完整正文和附件引用。用 `receivedMessageId` 完成回复的处理，原发件编号是 `sentMessageId`。
- `replyWait.status=matched` 表示收到关联回复，回复可以是阶段性反馈。全局或角色开关关闭、人类控制、会议焦点、取消、权限变动或到达等待期限也会结束这次调用。

## 在前端配置

打开办公室页头的 **等待回复**。设置按当前办公室的发信角色生效。未指定办公室的直接消息使用全局规则，回复默认继承原消息的办公室。

| 角色选项 | 行为 |
| --- | --- |
| 由角色选择 | 可随每条消息选择等待，省略时发完即返回。 |
| 每次必选 | 全局允许时，发送必须明确传 true 或 false。缺少选择时会提示补参数，消息尚未发送。 |
| 关闭等待 | 此角色在本办公室发完即返回，也会结束它正在进行的发信等待。 |

页头设置里可以关闭全局等待。最短等待窗口可在 **连接设置 → 发信后等待反馈** 修改。关闭全局或角色等待时，带 `waitForReply: true` 的发送返回 `replyWait.status=disabled`。独立的 `office_wait` 可继续使用。

已有设置升级时保留启用状态和原下限。重新启用后可以沿用保存的下限。

例如填 `300`（5 分钟）：角色请求等 10 秒，实际窗口为 `max(10,300)=300` 秒。期间收到关联回复即提前返回。

- `0` 表示不设下限，可设置 0–1800 秒。发信后单次最长等待 30 分钟。生成的宿主配置给调用留出 31 分钟（Codex 为 1860 秒，OpenCode 为 1860000 毫秒）。已有宿主配置需更新并重连，反向代理也要放行长调用。
- 配置对所有共用此数据库的 MCP 进程生效，只有人类管理者可以修改。采用版本核对，冲突不覆盖别人的更改，前端轮询不覆盖未保存草稿。
- 新的时长下限用于之后开始的发送等待；不追溯延长已在途的窗口。不强迫所有消息等待，也不改变独立 `office_wait` 的毫秒参数语义。
- 如果宿主自己提前取消请求、客户端期限过短或连接中断，服务器不能让客户端继续保持调用；这类情况应明确区分中断与正常超时。

## 超时、重试和身份

发送成功后超时，消息仍然已发送。结果保留 `sent=true`、`messageId` 和 `replyWait.status=timeout`；不要换一个发送键再发一遍。

在用户授权的等待范围内，使用**同一消息内容、同一 key**再次调用，可以继续等待而不重复投递。等待选项不参与消息内容的幂等哈希，可调整等待秒数，或改为普通发送查回原回执。幂等回执仍属于当前角色绑定；人类切换／解绑后须先恢复身份，不能把另一身份的键当作已有投递证明。

等待中发生错误会明确指出消息已发送，并保留编号、等待配置、错误原因与下一步；发送错误不会假装成功。调用被客户端取消时响应可能无法送达，但原发送回执不会被撤销。同一绑定重连后仍可按原键恢复。

如果关联回复已被本次发送等待领取、但响应丢失，按同一原发送 key 重试会恢复这条「处理中」消息，而不是再领取另一条回复；完成归档后不会自动重复投递。不同发送等待并发领取时，以原子事务避免重复领取同一条回复。普通独立 `office_wait` 仍只观察，不领取。

保持现有角色、办公室、会议室与附件权限。此功能不启动／恢复宿主，不向终端注入文字，不引入新软件或模型依赖。
