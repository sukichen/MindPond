# 跨角色记忆权限

用户可以指定一个角色协助查阅、整理同一账户下其他角色的私人知识。角色身份不变，普通检索和默认保存仍使用自己的记忆及当前办公室权限。

## 页面操作

在「角色与申请 → 打开角色 → 角色资料 → 记忆权限」设置：

- **允许查阅其他角色记忆**：可以检索、阅读其他角色的私人知识及关联、来源和修订记录。
- **允许替其他角色整理记忆**：同时具备查阅权限，还可新增、修改、删除、调整关联及执行已有整理流程。版本检查、图关联上限和来源保留规则仍适用。

两个开关默认关闭，更改自动保存。开启整理会开启查阅；关闭查阅会同时撤销整理。授权不包含人类记忆、目标角色的办公室记忆、私信、脚本和接续工作任务，不跨账户，也不能再授权其他角色。停用目标角色的知识可查阅，重新启用后才能代为整理。

合并、拆分不会转移这项授权；相关角色的跨角色授权重置为关闭，由用户重新设置。删除角色会清理其授权。不会自动合并、复制或整理任何知识。

## Agent 示例

先调用 `memory_identity` 检查自己的角色及 `delegation.readOthers / organizeOthers`，再用 `memory_roles` 查看获准查阅的角色目录。目录有分页；`nextAfterId` 非空时作为下一次 `afterId`。

假设目录中返回李四的 `id` 为 `<role-id>`，读取其知识：

```json
{"targetRoleId":"<role-id>","tool":"memory_search","arguments":{"query":"构建环境的已验证步骤"}}
```

以上传给 **Memory MCP 的 `memory_role_action`**。使用真实角色编号替换占位符。返回值明确区分实际操作者 `actor`、目标 `targetRole` 和工具 `result`。

取得完整正文后，确认确需修改且具有整理授权，再调用同一个工具：

```json
{"targetRoleId":"<role-id>","tool":"memory_update","arguments":{"nodeId":"<memory-id>","expectedUpdatedAt":1234567890,"content":"核验后的完整内容","reason":"核对实际环境后修订"}}
```

`expectedUpdatedAt` 必须使用刚读取的真实版本。`memory_save` 在这个显式作用域内写入目标角色，普通 `memory_save` 仍写入自己。需要整理流程时，先通过 `memory_action` 的 `describe:true` 查询 `memory_organization_claim/validate/commit` 等已有动作的参数，再把具体动作及参数传给 `memory_role_action`。一次调用只选一个角色；不能传 `officeId`、改变身份或嵌套委托。跨角色图关联仍然禁止。

## 撤权、重试与追溯

权限使用独立版本，与角色资料编辑分开。撤权或授权变化后，已有连接无需重连即可按新权限校验；向量生成等耗时工作在实际提交前再次校验，旧请求不能靠回执或整理任务编号绕过撤权。已经合法提交的修改不因后续撤权自动回滚。

整理操作沿用乐观版本、稳定操作键、独立修订记录和现有组织任务回执。审计记录保留真实操作者、目标角色及操作名称，不复制记忆正文。被拒绝时返回原因和下一步建议。

新增 `role_memory_permissions` 表；没有新增第三方依赖或模型调用。升级所有共用数据库的服务进程，重新连接 Memory MCP 以发现两个新工具；Office MCP 不增加记忆读写工具。
