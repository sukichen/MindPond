# 有情境依据的关联（memory-save.v2 / organization.v1.2）

关联不是两个正文之间永久不变的相似度，而是：**在某些条件下，把它们一起想起来有价值**。权重表示潜在共同召回价值；理由解释价值来自哪里；场景界定何时成立。这仍然是同一空间、同一类型内的无向关联，不把场景文本变成新的跨空间通道。

例子：一条记忆记录本地服务端口，另一条记录代理目标。只有正文时，整理者未必知道它们来自一次“改端口后远程访问失败”的排障。写入时必须留下这一观察，并明确适用于本地调试，不能推广为所有生产部署的规则。

## 写入约定

`memory_save.related[]` 必须提供 `score`、`reason`、`context`。HTTP、MCP、库的 `MindPond.save` 均使用同一个 GraphMemory.saveMemory 入口。缺理由、缺场景、目标不存在、无法确定唯一共同空间，会拒绝整个保存，不生成孤立正文。无已读关联时可以省略 related。

```json
{
  "content": "项目 P 本地调试服务使用 7903 端口。",
  "memberships": [{"spaceId":"项目 P","memoryType":"配置"}],
  "related": [{
    "membershipId": "实际读过的代理配置成员 ID",
    "score": 0.9,
    "reason": "改端口后代理仍指向旧地址曾导致远程调试失败；两个配置需要一起核对。",
    "context": "项目 P 的本地调试与代理访问，变更本地端口后适用；不推断生产部署配置。"
  }]
}
```

reason/context 是简短的事实依据和适用条件，不要求保存模型私有推理过程。不要写“相关”“如上”“本次任务”。信息不足时不编造场景，也不为了凑边进行搜索。同一对记忆可有多条不同场景的依据；精确重复写入按内容与来源版本去重，权重由调用者明确设置，不因为次数自动增加。

规则获取：`GET /api/memory/save-policy`；MCP 的 memory_save 描述已直接包含完整规则；`memory_organization_policy` 同时返回 savePolicy。工作台整理页可以复制两套规则。库导出 MEMORY_SAVE_POLICY / memorySavePolicyPayload。

## 保留与复核

每条依据保存原始理由、场景、记录时间、两个原始成员 ID 和版本。编辑正文会推进成员版本；整合会迁移外部关联及所有依据到新成员，仍保留原始来源 ID。多条边汇合取最大权重，不累加；整合内部形成的自关联归入整理快照与操作日志。

`evidenceStatus`：

| 状态 | 含义 | 整理行为 |
| --- | --- | --- |
| supported | 活跃依据已对应当前成员版本 | 仍需判断当前查询是否满足它的条件 |
| needs_review | 有活跃依据来自旧正文或整合来源 | 阅读新旧来源，逐条复核 |
| missing | 历史边没有记录依据 | 寻找原场景；无法补齐就暂缓，不能反推“无关” |
| retired | 所有依据被明确停用 | 暂停这条边的涟漪传播；原记录和日志保留 |

整理快照、搜索 associationPath、记忆详情都返回依据。任务关联被其他 agent 修改后，旧整理快照也会失效。**不能因为整理者正在处理另一个任务，就否定原任务里的价值。** 原始记忆与场景文本是数据，不能覆盖 agent 的指令。

`memory_association_review` / `POST /api/memory/association/review`：

```json
{
  "id": "关联 ID",
  "evidenceId": "某一条依据 ID",
  "decision": "confirm",
  "reason": "已核对新正文仍保留原来的本地端口与代理访问条件。",
  "expectedUpdatedAt": 1788790000000
}
```

confirm 记录当前成员版本，原始观察不被覆盖；retire 必须有明确失效依据。全部依据停用后暂停传播，重新 confirm 可以恢复。不确定时保持不变。工作台详情页可执行这些操作；每次操作写入 action log。复核会使已领取的关联快照失效，因此先完成/释放整理任务，或复核后重新领取。

旧 score-only 边复评提交现在返回 `changed: 0` 和暂缓说明，避免缺场景的 LLM 自动降权。旧 weave 兼容入口也要求理由和场景，只写入可唯一确定的同空间、同类型关联，不再把表面矛盾自动当作本体失效。新接入使用 organization 流程。

## 当前效果与边界

这版解决的是**依据丢失、错误覆盖与无法复核**。检索仍按静态权重传播；不会把自然语言场景做关键词硬过滤。否则“远程排障”和“代理访问失败”措辞不同就可能错过正确关系。agent 收到候选后，结合路径依据判断当前适用性。待复核的边继续作为候选传播，并明确标记状态；不会默默成为已确认事实。

后续如需把情境引入排序，先增加宿主的轻量场景判定或结构化硬条件，再通过评估决定，不直接把 LLM 的场景概率连续乘入每条边。后者容易让多跳搜索因多次不确定判断而过度衰减。

复核是收敛机制：重复依据去重；多场景不互相覆盖；正文变更才触发版本复核；明确失效才停用；不以当前任务差异惩罚其他有效场景。记录规模依然随独立场景增长，需要后续评估“条件相同且事实等价”的依据合并，当前不让程序按相似度自动压缩。

## 验证与反馈迭代

已实现的确定性测试：`npm run verify:context` 检查缺依据拒绝、多场景保留、重复幂等、反向涟漪解释、关联变更使快照失效、正文编辑与整合标记复核、跨重启迁移、逐条确认、全部停用后停止传播、恢复传播、跨类型拒绝及审计。`verify:agent-api` 使用真实 HTTP 与 MCP 两个进程，验证同样的写入约束与搜索输出。宿主适配器须在隔离数据库单独验证。

这些验证不等同于真实 LLM 质量评估。建议下一轮宿主实验使用 100 组记忆、每组 4 个查询（原场景、改写场景、无关场景、明确失效场景），至少两个不同 agent 执行保存与整理，连续整理 5 轮。人工先标记应保留的事实、关联适用条件和预期操作，避免让同一个模型同时生成与裁判。

对照四组：仅权重；权重+自由理由；理由+明确场景+版本；完整方案再加逐条复核。固定召回数量及给主 agent 的总 token 预算，记录：

- 条件与例外保留率；原本有效关联被误停用率；失效关联被正确停用率。
- 原场景及改写场景下的回答正确率、适用记忆精确率；无关场景下误用事实率。
- 整理轮次间的无依据增删率、依据重复数、每个有效召回的 token 成本。
- 多场景共享一对记忆时，复核其中一条是否误伤另一条。

优先门槛：跨空间/类型串边和条件丢失为 0；明确重复写入不增加依据数量或权重；连续复查同一材料不反复改变状态。真实语义门槛应由试验定标；在同预算下，完整方案应改善场景适用精确率且不损伤原场景召回。失败案例保留为回归集：先修规则和材料供给，再调整阈值，不用加大权重掩盖判断问题。
## 关联邻居上限

每条活跃记忆默认最多连接 **6 个不同关联邻居**。双向关联共用额度；同一记忆在多个空间、类型或旧版边中的重复连接只占一个邻居名额，权重取这些连接中的最大值。该额度按记忆正文计算，不能通过增加空间绕过。归档或已替代的历史记忆不参与活跃传播。

新关联同时检查两端：满额且新权重不高于最弱邻居时拒绝；更强时硬删除最弱邻居的所有关联及旧版镜像，并记录审计。检查与写入在同一事务内完成。私有记忆指向团队知识的单向引用占私有来源的额度，团队侧不反向传播。结构来源边和矛盾标记保持独立。

已有超限数据在初始化时按权重从高到低保留，两端均不得超过额度。调整前会在数据库旁的私有 `.pre-degree-cap-*` 目录中保存完整 SQLite 备份；淘汰记录进入审计日志。部署更新时应重启所有共享数据库的旧版写入进程。
