# 协作产品改造方案：接入向导与任务办公室

实现进度：HTTP MCP 独立身份、显式工作会话/受限分工、MCP 内指南、项目与办公室、定向问答、负责权移交、文本包、精确轮次验收及前端向导已实现，参见[当前使用说明](../collaboration-offices.md)。以下保留原设计与完整验收目标；OAuth、浏览器 SSE 观察及各实际宿主的逐聊天隔离验收不作为已完成能力。

日期：2026-10-15。状态：设计提案，尚未实现。本次按本地 `1925200` 的实际接口和页面核对；本文中的新接口、字段、页面及验收目标均为拟议内容，不能当作现有能力。

接入凭据、同一 agent 多聊天角色、MCP 内教学及隔离边界详见[身份与会话补充设计](collaboration-auth-sessions-2026-10-15.md)；该文细化本文的身份模型，实施时一并验收。

## 1. 产品目标与不可变约束

用户应该不读协议文档就能完成：接入两个 agent → 指定谁做什么 → 发起一个共同任务 → 看懂谁在处理、谁在等谁、为什么卡住 → 打开真实消息和证据 → 决定继续或停止。

**所有 agent 仅通过 HTTP(S) Streamable HTTP MCP 访问 MindPond。** 记忆、身份发现、任务、消息、等待、进度、证据全部在这条通道完成。接入向导不生成 stdio 配置，不在背后启动 stdio→HTTP 桥，不使用宿主 native 插件、直接 SQLite/SDK、REST 或共享 MindPond 数据目录。客户端原生 HTTP MCP 不可用时，明确显示该版本尚不支持接入，而不是悄悄换传输。

浏览器是用户管理端，通过受认证的 Web 后端进行配置和观察；它不是 agent 的第二条接入路径。agent 凭据不得调用管理 REST。后端复用同一协作服务进行权限、幂等、版本与日志处理。

MindPond 继续作为被动协作基础设施：保存、路由、鉴权、回执、等待、状态投影。不托管 LLM，不启动/唤醒 agent，不接管宿主的工具执行权限。两个 agent 要继续迭代，都必须有仍在运行且愿意继续调用工具的宿主。

协作不要求 agent 共享磁盘。默认只交换通过 MCP 明确发布的文本；路径、文件名、仓库 URL 或私有 memory ID 都不等于已经交付材料。

## 3. 先统一用户能理解的概念

| 页面名称 | 含义 | 例子 | 与其它概念的区别 |
|---|---|---|---|
| 账户 | 权限和数据授权归属，不是机器/IP | account-a、account-b | 一个账户可接入多个 agent，可在多台机器使用 |
| Agent | 一个独立接入、可管理的宿主身份 | 我的 Codex、我的 OpenCode | 服务端认证绑定；角色不作为它的全局可变属性 |
| 工作会话与分工 | 该 agent 在一段工作上下文中承担的职责 | Codex · 会话 A · 开发 | 对应办公室工位；同一 agent 可有不同角色的多个工位 |
| 本次连接 | 一次 MCP 传输连接 | Codex 与 MindPond 的一次连接 | 不一定对应一段聊天，断线不删除 agent 或工作会话 |
| 协作项目（workspace） | 可复用的成员、权限和任务集合 | AI 教师开发 | 不是共享文件夹，也不是记忆 domain |
| 任务办公室（office） | 一个共同目标及其参与者、工作项、消息与证据 | 排查通知播放失败 | 一个顶层任务对应一个办公室；项目内可有多个办公室 |
| 工作项 | 办公室中的具体分工 | 复现、修复、独立验证 | 有负责人、依赖和验收；不会因发送一条消息自动完成 |
| 记忆范围（domain） | 长期/临时知识的归属和访问授权 | 当前会话、个人、团队 | 协作成员资格不自动授予别人的私人记忆或团队发布权 |
| 记忆空间（space） | 项目/语义组织与涟漪边界 | project:ai-tutor | 不承担账户访问控制，也不是文件访问组 |
| 文件访问组 | 已声明或经过探测的某套项目材料访问关系 | 仓库 A 的共享工作副本 | 不由同账户、同局域网或相同路径名推断 |

普通流程用“协作项目”“任务办公室”“添加 agent”“谁来做”“谁来验收”。domain、principal、lease、seq、expectedRevision 放在说明/高级详情中。不要让用户先建立 team domain 才能进行个人多 agent 协作。

办公室、成员与消息属于协作业务数据，不自动变成知识图谱节点；协作关系不套用知识节点的六邻居限制。办公室成员也不自动共享 session 记忆。v2 默认用可信 principal + agentId + 宿主逻辑 session 隔离会话，保留同一 agent 重连恢复的能力；共享会话须另外显式选择，不能拿 officeId 自动把所有人的 session 合在一起。

个人多 agent 的初始选择只问一句：**这些接入账户是否也共享你的长期个人记忆？**

- 只共享协作任务和已发布材料：保持原有记忆授权不变，作为新协作的安全默认值。
- 同时共享本人指定的个人记忆范围：用户选择已有范围并明确确认授权变更。
- 团队知识另设高级选项；进入办公室、完成任务均不自动发布长期团队记忆。

## 4. 接入与配置：普通用户实际走什么流程

### 4.1 首次打开协作页面

空状态显示“连接你的第一个 agent”，下面用三步图说明：添加接入身份 → 在宿主中配置 HTTP MCP → 完成一次握手。首次管理身份建立一次即可，之后显示当前用户，不常驻三个密钥输入框。

若 Web 工作台和中心 MCP 是独立进程，首次设置核对它们的 `serviceInstanceId`/`memoryStoreId`，确认使用同一个实例。用户只需识别“工作台已连到这个 MindPond”；不要求输入数据库文件路径。普通 agent 永远不能选择服务端 DB。

### 4.2 “添加 Agent”向导

1. **名字和用途**：显示名、宿主类型、所属账户。示例“我的 Codex”。“会话 A · 开发”在安排具体办公室分工时设置，不作为全局身份。不让 LLM 自填有权限效力的 agentId。
2. **协作权限**：选择可进入的协作项目和角色，以中文解释“发起问题 / 处理任务 / 验收结果”。高级选项才显示底层值。
3. **HTTP MCP 接入**：展示中心 `/mcp` URL，按宿主和已验证版本生成原生 HTTP MCP 模板。凭据在用户设置层保存/引用，不能放入 agent 提示词、聊天记录、URL 查询参数或 Git。模板不创建本地 DB/模型，也不启动桥接器。
4. **检查连接**：等待该凭据对应连接完成 MCP 初始化，再等待 `work_bootstrap` 确认。这两项分别显示“连接成功”和“已发现协作工具”。仅页面创建了一条记录时显示“待接入”。
5. **加入办公室**：选择已有办公室或创建第一个任务，展示一句可直接交给宿主的启动提示词。

页面可以签发、撤销、轮换该 agent 的最小权限凭据；**页面添加记录不会自动安装或启动另一台机器的 agent**。同一 agent 多个工作会话和同时连接，在详情分别显示。租约绑定工作会话/分工及其 epoch，连接变化按恢复协议处理，不能把连接等同聊天。token 由宿主 MCP 客户端管理和发送，LLM 不获取 token；显式会话编号仅用于定位，强角色隔离另需受限凭据与宿主实际隔离能力。

原生 HTTP 模板必须有独立的客户端/版本验证矩阵。未知版本显示“待验证”及 URL/认证要求，不编造一键兼容。URL 支持 HTTPS 和用户明确选择的内网 HTTP；地址不写死某个 LAN IP/端口。

### 4.3 文件条件不放进注册必填项

文件可见性通常随项目、机器、checkout 和权限变化，在进入办公室时配置：

- 我们能读取同一份共享工作副本。
- 我们有各自的仓库副本，需要同步版本。
- 我们看不到对方文件，只能中转文本。
- 还不确定，稍后确认。

“同一份共享工作副本”与“同仓库两个 clone”分开。即使能读同一副本，也要确认只读/可写、当前提交与未提交改动；不要用同一颜色暗示验证的是同一代码版本。

### 4.4 出错时应告诉用户什么

| 状态 | 页面给出的下一步 |
|---|---|
| 记录已创建但未握手 | 在目标宿主配置这条 HTTP MCP 连接，再执行显示的启动提示词 |
| 凭据无效/已撤销 | 回到该 agent 的连接设置重新签发/更换，不让 agent 猜身份 |
| MCP 已连但没调用 bootstrap | 给出一条“检查你的 MindPond 身份和收件箱”的提示词 |
| 已认证但未获项目授权 | 用户选择并授予该协作项目，不展示一个空列表让人猜 |
| 目标 agent 没有活跃等待 | 显示“已排队；对方下次读取收件箱可见”，不说正在处理 |
| 工作台与 MCP 对不上 | 说明两个地址属于不同实例，停止配置提交 |

## 5. 任务办公室的页面结构

### 5.1 总览

主导航为“办公室 / Agents / 协作项目 / 设置”。办公室列表显示目标、参与者、当前阶段、正在等待的对象、最近真实更新；避免把所有历史任务堆成角色卡片墙。

创建办公室只填：目标、验收方法、参与者、初始分工、材料条件；多轮协作再补最大轮数/截止条件。问题报告仍有结构化完整性要求，但表单按“发生什么—怎么复现—现有证据—希望怎样算完成”展开，未知可以明确填写未知，不强制编造。

### 5.2 办公室内

- 顶栏：目标、所属项目、运行/暂停/待人工/完成、停止操作。
- 中央：2D/轻量 2.5D 办公室，每个参与工作会话/分工有工位和名字；初期 2–6 人清晰展示。同一注册 agent 的多个角色工位显示关联标记，避免看成同一个角色来回切换。
- 工位标识：角色、当前工作项、当前状态、最近观察时间、连接情况。
- 关系：带方向的曲线和消息包，标“交给你处理 / 请回复 / 补充证据 / 提交验收”。
- 右侧详情：选中的 agent、交互或工作项；展示摘要、简短行动理由、版本、文件可见性、实际材料和回执。
- 底部时间线：可回看真实事件；新消息与历史回放明确区分。

桌面支持画布视图与列表视图互切。手机默认任务/消息列表，顶部保留紧凑办公室概览，点人物或关系打开底部详情；不能靠捏合巨大画布才能阅读正文。320px 下仍能找到“谁在等谁”“缺什么材料”“停止任务”。

人物间曲线表达逻辑收发关系，实际消息始终经 MindPond HTTP MCP；共享文件时也不建立 agent 之间的旁路通信。初期 2–6 个工位是画面可读性目标，不是协议人数硬上限。

### 5.3 角色外观和工作服

工作服的主颜色/纹理表示**本办公室当前选中的文件访问组**，胸牌文字表示“仓库 A”“文本中转”“待确认”。角色用名称和小标识表达，不复用记忆 dimension 的颜色。

同色制服只表示具有同一已确认访问组，旁边仍要写“同一工作副本 / 独立副本”“只读 / 可写”和版本状态。未确认时用中性制服和问号，不默认大家共享文件。

一个 agent 能访问多个材料组时，胸牌显示当前组和“+2”，详情列全表。访问关系非对称或不具传递性时，不能强塞为单一组：显示 A→B 的实际访问矩阵；衣服只是概览，判断交付是否足够必须落到具体材料。

## 6. 分清六种交互，而不是所有东西都叫 handoff

| 用户动作 | 协议语义 | 责任与等待 | 画面 |
|---|---|---|---|
| 告诉他 | `inform` | 单向通知；不要求业务回复 | 一次消息流，停在对方收件盘；无“等他”链 |
| 问他，等回复 | `request/reply` | 绑定 requestId、收件人、请求版本；只有匹配回复解锁 | 发起者工位显示“等 OpenCode 回答 Q7”，对方显示待回复事项 |
| 委托他做一件事 | `delegate` | 新子工作项；父任务负责人不变，结果满足子任务验收后回报 | 子任务文件夹移至对方工位，父任务保留负责人 |
| 将负责权移交给他 | `transfer` | 两阶段；对方明确接受前，原负责人继续负责 | 工位间待接收连线；接受后负责人标记真正移动 |
| 提交这版给他验收 | 复用 iteration submission | 绑定 roundId、codeVersion、材料摘要；不能凭“已读”继续改下一版 | 代码/文本包流向验收工位，作者转为等待 |
| 反馈结果 | verification / final reply | 通过、需修改、条件不足分别记录，不混成完成 | 反馈回到对应轮次；返工、完成或缺材料状态不同 |

v1 `work_handoff` 是“新建问题交接”，不等于已经支持一般负责权转移。v1 `work_reply` 是讨论文本，不等于已经支持有精确关联的等待答复。新版本必须补齐后端语义后才开放这些 UI 按钮。

### 6.1 三条独立状态轴

1. 工作项：未开始 → 处理中 → 已提交 → 已验收；阻塞、取消为明确分支。
2. 消息：已发布 → 服务端已排队 → 对方已读 → 对方接受/回复。不同动作可没有后两步。
3. 连接/运行观察：待接入、已握手、最近有动作、当前有等待调用、连接中断、未知。

不要把“HTTP 连上”“已读”“等待超时”“模型返回一句已完成”都映射为正在工作或任务完成。单个 agent 可以同时持有多个请求的等待状态；每条请求保留自己的接收者/版本/终态，不用一个全局 waiting 布尔值覆盖。

### 6.2 请求、移交和循环的边界

- 回复必须指向当前 requestId/version，且作者是被指定 agent；普通聊天、旧回复、别人代答、已读回执不能解除业务等待。
- request 可有多次补充，显式 `finalReply` 才满足“等最终答案”；补充问题可产生自己的关联请求。
- transfer 创建时记录当前 assignmentEpoch；接受时在事务内检查权限、任务版本及当前负责人。成功接受才递增 epoch、撤销旧租约。目标拒绝/未接收不留下无人负责状态。
- 两个 agent 同时领取只有一个成功；旧连接/旧 epoch 的租约不能提交。
- `work_wait` 沿用有界长等待，不持 DB 锁。超时为 pending，返回 resume；宿主预算允许才继续调用。不能承诺“永远自动等到回复、永不结束”。
- 根办公室控制迭代轮数、截止、允许参与者和执行范围；新建子任务/请求不能绕过根预算。依赖形成循环、A 等 B 且 B 等 A 时显示等待环，提示继续所缺输入，不伪装两人都忙。
- 用户取消、撤权、版本取代和达到预算时结束对应等待；暂停保留消息与证据。取消/暂停阻止后续业务提交，但不能宣称已强行杀死远端宿主进程。

## 7. 看不到文件时，如何真的协作

### 7.1 文件可见性是一条带证据和有效期的观察

记录内容包括：办公室、agent/本次运行、材料组、资源集合、读写权限、共享副本/独立副本、代码版本、观察方式和时间。`unknown`、用户声明、agent 自报、双端探测通过、过期/被否定分别显示。

用户声明“它们共享目录”不能冒充服务端已验证。需要验证时由双方经 HTTP MCP 发布对指定非敏感文件的摘要/版本或用户批准的探测结果；MindPond 只比较报告，不读取任何本地路径。相同 hash 只能支持指定文件快照相同，不能证明整个文件系统共享或读写权限相同。变化/断线后保留旧观察但标注时效，不能继续冒称当前可访问。

### 7.2 文本证据包

发送方调用 MCP 发布必要文本及清单，接收方用 MCP 分页/分段读取：

- 报告、复现步骤、环境条件、错误原文、已经尝试过什么。
- 代码片段：文件逻辑名、语言、基准版本、范围、必要上下文。
- 文本 patch：base commit、patch digest、涉及文件，说明是否含未提交改动。
- 测试命令与原始输出、退出码；假设和事实分开。
- 清单：完整/节选、正文 UTF-8 字节数、分段数量、整体 digest、发布与修订版本。

digest 是一致性依据，不证明发送方描述真实。commit 一样但 dirty patch 不同，仍是不同待验证产物。接收方先记录“材料已读取”，在自己的环境复现/应用后另报实际检查结果；不把读取完成当作验收通过。

发布到只支持文本的服务时，二进制/图片只登记“尚不能交付”的缺口，不偷用 base64 将其冒充文本，不根据无法访问的截图给通过结论。可由发送者提取必要文字，或由用户另行提供允许访问的外部材料；路径/URL 仍须接收方确认真实可获取。

大文本按服务端公布的 byte/chunk/office quota 分段；先写未发布材料，再原子 finalize 清单，防半包可见。发重试复用稳定 key。接收方缺任意段或 digest 不匹配时显示“材料未齐”，不得默默截断。每个面板显示“已送正文 / 仅引用 / 读取完成 / 不可访问 / 待补充”。

### 7.3 相同任务的两条路线

共享文件路线：Codex 修改 → 发布精确版本/dirty 摘要 → OpenCode 确认其可见产物 → 跑验证 → 回传实际输出 → Codex 收到匹配反馈。

文本中转路线：Codex 修改 → 发布 patch/必要代码/复现资料 → MindPond 保持完整文本包 → OpenCode 读取并确认可用 → 在其环境应用或指出缺少基准 → 验证/阻塞反馈 → Codex 补充/继续。

两条路线都在办公室展示。文本中转中，消息包经过中央资料台；共享副本路线展示版本引用。没有交付正文、接收者又看不到引用时，立即显示缺材料，不能让“验证中”动画一直转。

## 8. 动画必须有事件依据

| 真实事件 | 展示 | 不能暗示的事情 |
|---|---|---|
| 服务器提交消息成功 | 消息包一次流动到收件盘 | 对方已看见或已开始 |
| 接收方显式 ack | 收件盘变为已读/接受 | 已完成任务 |
| 取得有效租约 | 工位显示当前工作项与“已领取” | 正在执行某条看不到的本地命令 |
| agent 上报 progress + 简短 why | 工位和详情显示具体动作、依据来源 | MindPond 独立观察了其代码/测试或拥有完整思考过程 |
| 发布/读取文本材料 | 资料台与接收方出现材料状态变化 | 能访问整个文件系统 |
| 当前存在 work_wait 调用 | 等待线连至对应对象，附等待条件 | 已退出宿主会自动醒来 |
| 验收反馈落库 | 对应轮次流回；展示原证据 | MindPond 自己跑过测试 |
| 断线/时间窗口过期 | 降为“最近观察/当前状态未知” | 自动认定失败或偷偷继续下一轮 |

所有动画可点开对应 seq/eventId 与真实正文。历史回放、初次快照与断线补报不伪装实时新动作。一个事件只播放一次；补报集中摘要且可展开，不制造大量重复往返。

同屏高频事件合并动效但不丢日志；隐藏页面暂停动画，恢复后先同步状态。支持减少动态效果。正常读取不自动确认已读；观察者不能代 agent 领取或接受。

MindPond 只能自动观察自己处理的 MCP 动作。本地 grep、编辑和测试需要 agent 用 HTTP MCP 阶段性报告；不能在没有插件/宿主上报的前提下宣称捕获所有本地工具动作。why 是简短任务解释，不请求或保存模型私有思维链。

私人记忆 read/save 若展示到办公室，默认仅给不含正文/标题/私有 ID 的授权状态摘要，且须绑定当前办公室。展示某条记忆正文仍要单独检查观察者权限。协作空间成员不能借办公室动画读取另一个 agent 的个人/session 内容。

## 9. 后端与协议设计

### 9.1 身份不能只靠 principal

```text
Account / principal（权限主体）
  └─ RegisteredAgent（显示身份、被指定的收件人）
       ├─ Credential（可撤销、可轮换，服务端绑定 agentId）
       ├─ AgentConnection / run（多个当前连接，不等同聊天）
       └─ WorkSession（可恢复的工作上下文）
            └─ RoleAssignment / seat（办公室分工、授权与修订）

CollaborationWorkspace（项目 ACL）
  └─ Office（根目标、参与者、根预算）
       ├─ WorkItem（具体分工、assignmentEpoch、租约）
       ├─ Exchange（inform/request/reply/transfer）
       ├─ ArtifactManifest + TextChunk（明确发布的文本）
       └─ Event / Delivery / Ack / Wait / Projection
```

可信调用上下文增加服务器绑定的 `agentId`、`credentialId`、`connectionId`，以及经服务端授权校验的 `workSessionId`、`assignmentId`、`bindingRevision`，保留 principal/domain 授权。MCP 工具参数中的名字/agentId 只可指定目标，不能决定发送者。clientInfo 仅为宿主自报信息，不能用来认证身份。显式上下文模式不假称能阻止同一广授权凭据选择另一个合法分工；独立验收需要受限接入和宿主隔离。

项目可用角色 = 账户的项目角色 ∩ 对该 agent 的限制；办公室新成员必须先具备项目权限并经已授权的成员管理策略确认。新办公室默认参与者及授权观察者可见；旧项目级可见的任务迁移时显式保留旧可见范围并标注，不假称变成私聊。

投递/ack/租约/等待/幂等键都要绑定 agent 身份；同 principal 下两个 agent 不能互相冒名接收、领任务或命中同一份回执。凭据轮换不改变稳定 agentId，撤销旧凭据必须影响悬挂等待和重放。用户通过页面代为调度时记录用户身份与原因，绝不能伪造 agent 已读或已接受。

### 9.2 新的接入注册与已有凭据配置

v1 的 grant 文件有 principal 唯一约束，不能只加一个 agent 昵称字段。v2 至少支持一 principal 的多个 agent grant，兼容导入旧文件：每个旧 grant 映射为一个稳定的 legacy agent，旧 key 不自动获得更多权限。

如果初期继续使用文件存凭据摘要、SQLite 存 registry，不能谎称跨文件和 DB 是一次事务：使用 pending → active 的 provisioning 操作。DB 先登记 pending，持锁原子写 grant，再将 registry 激活；网关同时检查二者 active。中断后可恢复/撤销，不能留下孤儿 key 已授权但页面显示失败。后续若统一存储需单独迁移，不能维护两个相互竞争的权限真相。

### 9.3 HTTP MCP 工具面，命名为候选

| 面向 agent 的能力 | 拟议工具/复用工具 | 一次调用要返回什么 |
|---|---|---|
| 发现身份和下一步 | 新 `work_bootstrap` | 服务实例、可信 agent、项目/办公室、未读数、工具协议版本、短规则和可执行下一步 |
| 建立工作上下文/按需学规则 | 新 `work_session_open`、`work_guide_get` | 用户已授权分工的绑定结果、无秘密上下文编号、直接可读的版本化指南；多候选不猜 |
| 获取办公室全文/增量 | 新 `work_office_get`，复用 inbox | 分页完整材料、当前状态与游标，不能截断正文冒充完整 |
| 发送通知/提问/答复 | 新 `work_message_send` | 稳定 message/requestId、发布 seq、投递状态；可同时请求返回 wait 的 resume 条件 |
| 委托/负责权移交 | 扩展 work task / 新 transfer | 根预算、负责人、接受条件、revision；拒绝不改负责人 |
| 文本中转 | 新 `work_material_publish/get` | 可分段、可恢复的正文与 finalized 清单；发布不是接收方读取 |
| 报告进展/文件可见性 | 新 `work_progress` / `work_access_report` | 实际 actor、观察方式/时间、短 why、明确自报来源 |
| 挂起等待 | 扩展 `work_wait` | 支持 request_reply/transfer_response，保留精确迭代条件、超时 pending 与 resume |
| 验收 | 复用 iteration_submit / verification_report | 绑定本轮代码和材料 digest，不能用通用完成按钮绕过 |

不要一次向默认工具目录注入几十个新工具。首轮发现靠 bootstrap/现有 protocol rules，按角色返回短操作建议，详细字段按需发现。向后兼容旧工具，但旧身份不能假装有 v2 agent 定向语义；接口响应包含协议能力版本。

### 9.4 事件和投影

底层保留现有 SQLite、Coordinator、版本检查和动作日志。按职责增量提取 AgentRegistry、OfficeStore、ExchangeStore、TextMaterialStore、OfficeProjection，避免把注册、渲染投影和所有业务继续塞入一个类。

事件 envelope 至少含 serviceInstanceId、seq/eventId、workspaceId、officeId、workItemId、actorPrincipal、actorAgentId、recipientAgentIds、kind、serverTime、相关 request/round/material version。所有字段按观察者权限裁剪。连接状态是可过期观察，业务事件是持久事实，不能混用生命周期。

前端使用同一认证会话的 snapshot + cursor 增量订阅，优先 Web SSE，失败回退到共享有界轮询；**该观察通道只面向浏览器，不成为 agent 接口**。MCP 客户端继续 inbox/work_wait；MCP 通知只能作提示，不能代替持久投递。

快照与 high-watermark 在一致读内生成；重连按游标补报并去重。全局 seq 因权限过滤产生的数字间隔不能被误判为丢包。权限撤销时终止观察和等待，不只在连接建立时校验。UI 重建投影不重播旧动画、不丢草稿、不自动 ack。

## 10. MCP 被动条件下，怎样让宿主实际配合

服务初始化的简短 instructions、工具描述及 bootstrap 返回共同教这五件事；完整规则通过 MCP guide 工具按需返回，不要求本地文档或 resources 能力：

1. 实质任务开始/重连时调用 bootstrap，确认可信身份、当前工作会话与办公室分工；看未读收件箱。身份有歧义时明确选择，不切换到全局最后活跃角色。
2. 要另一位参与者做事，用明确类型发出请求/委托，附自包含材料。不能只在聊天中说“交给他了”。
3. 看不到文件时发布必要文本；不凭路径当交付，不凭摘要伪称完成测试。
4. 发出需要答复的请求后按返回条件等待；只处理匹配的当前请求/轮次，不因超时开始下一轮。
5. 关键动作后报告短进展和原因，提交实际结果与证据；缺条件就说明阻塞。

向导最后给用户的示例提示词：

> 使用已经配置好的 MindPond HTTP MCP，先确认你的 agent 身份和可用办公室，并读取收件箱。在“修复登录失败”的办公室中负责开发；需要验证时向指定的 OpenCode 发起验收请求。看不到对方文件时发布完整的必要文本材料。提交后等待匹配的本轮结果，按反馈继续，最多三轮；条件不足时停下说明，不把发布、已读或超时当作验证通过。

示例不含 URL 凭据，不强依赖某种 agent 品牌。纯 HTTP MCP 可以降低协作摩擦，无法强制所有宿主永久调用工具、跨退出续跑或上报每一步；这些限制要作为当前状态展示，不能由动画掩盖。

## 11. 实施顺序与每阶段验收

### D0：产品交互与协议冻结

产物：本文、接入向导流程稿、办公室示意、三条事件故事（共享副本验证 / 文本中转 / 问答等待）。冻结术语、交互类型、状态轴、身份与文件组含义。

验收：找未读过源码的人完成纸面操作，能解释 workspace/domain、知道如何添加 agent、知道哪两人能看同一份文件、能识别未接收与已完成。改过文案后再进入 D1，不用加更多 JSON 示例代替可用性。

### D1：真实 HTTP 接入和独立 agent 身份

入口：`network-config.ts`、`network-server.ts`、`trust.ts`、`collaboration.ts`；新增受控注册管理、WorkSession/RoleAssignment、bootstrap/guide、HTTP 配置导出和接入向导。先处理多 agent 凭据/投递隔离、逐分工上下文与 v1 migration，再改前端名字。新增验收同时覆盖身份与会话补充设计的矩阵。

验收：同账户两套独立 HTTP MCP SDK 客户端注册/握手/收件箱互不混淆；跨机器字段不影响身份；无任何 stdio/native/SDK 访问 MindPond；失败注册可恢复；页面能明确解释未连接/未授权。

### D2：办公室、定向消息与文本交付

入口：现有 collaboration/coordination、工具 schema、HTTP gateway；增加 office/work item、request/reply、transfer、材料包与等待关联。复用既有 iteration 验证守卫。

验收：不共享文件的两个真实 HTTP MCP 客户端完成“报告 → 请求必要代码 → 发布文本/patch → 读取 → 验证反馈”；发送路径不触发假完成。相同账户不同 agent 不可代答/接受。完成责任转移、请求取消、旧结果拒绝的状态机验证。

### D3：真实事件驱动的办公室前端

入口：重构 `web/collaboration.*` 与 `collaboration-loop.js`；办公室场景只消费服务端投影，保留完整文本详情/时间线/列表兜底。建立浏览器订阅与重连恢复。

验收：每条动效能追溯真实事件；已读不等于完成；角色不会随机来回跑；文本中转缺口与文件版本差异可直接看到。手机和减少动态效果模式不丢信息。

### D4：真实宿主试用与发布

用用户选定的两种原生 HTTP MCP 宿主做三条真实任务，不以 SDK 脚本冒充真实 LLM 行为。记录客户端版本、配置方式、是否主动发现 bootstrap、消息材料是否足够、人工纠正次数与等待恢复。

完整功能在 D1–D3 验收后才替换原页面默认入口。旧线程只读可访问、旧链接仍可定位；发布包 `files`、release fixture 和网络/协作回归同步更新。此阶段不引入强 LLM、二进制中转或 agent 进程托管。

## 12. 必测矩阵

| 编号 | 场景 | 必须看到/保证 |
|---|---|---|
| C01 | 初次用户添加 agent | 不编辑 JSON、不输入三种 key，能走到待握手/已接入 |
| C02 | 原生 HTTP 连接验证 | 请求经过 MCP HTTP 网关；无 stdio bridge/native adapter/DB 客户端 |
| C03 | 同 principal 的两个 agent | 各自收件箱、ack、lease、receipt 不混淆；伪造发送者字段无效 |
| C04 | 相同 agent 的两次连接 | 工作项单一租约持有者；旧连接不能覆盖新 epoch |
| C05 | 页面注册在任一落盘阶段中断 | pending 可恢复/撤销，没有隐形已授权凭据 |
| C06 | token 撤销/角色撤销时正在等待或重放 | 立即拒绝/结束，不借旧 receipt 恢复权限 |
| C07 | 通知与请求 | inform 无业务等待；只有匹配 requestId/version 的最终回复解锁 |
| C08 | publish 后立即 reply，sender 再 wait | 已存回复立即匹配，不丢竞态消息 |
| C09 | 旧回复、普通讨论、别人代答 | 不能解除当前请求等待或完成本轮验收 |
| C10 | A 转交 B，B 未接受/拒绝 | A 仍负责；B 接受后原子转移，旧 lease 被 fencing |
| C11 | 两人互等/父子任务等待成环 | 可见等待对象和环，不能一直显示都在执行 |
| C12 | 同 LAN/同路径名/同账户 | 不推断文件共享；独立 clone 不显示为同一工作副本 |
| C13 | 同 commit 不同未提交 patch | 版本差异可见，不能错误确认同一待验产物 |
| C14 | 只有对方看不到的路径引用 | 显示缺材料，不允许据此报验证通过 |
| C15 | 文本包分段中断、重复、缺段、超限 | 保留重试与完整性状态；未 finalize 不给半包成功 |
| C16 | 接收完整文本但无法复现环境 | 显示 blocked 和条件差异，不能等同已验证 |
| C17 | 真实 work_wait 超时/宿主退出 | pending/无活跃等待分别展示，不自动推进或宣称唤醒 |
| C18 | UI 重连、重复/乱序/历史事件 | 状态可重建；同事件不重复动效；ACL 序号间隔不假报丢包 |
| C19 | 办公室中发生私人 memory read/save | 不泄露未授权正文、标题、ID；不自动晋升 team |
| C20 | 用户在页面代为操作 | 明确记录用户 actor，不伪造 agent read/accepted |
| C21 | 320/390px、键盘、减少动态效果 | 文本和控件无横向溢出，关键状态和操作不靠 hover/颜色 |
| C22 | 12/50 人、1万事件、事件突发 | 分组/列表/有界 DOM 与动效；审计不因动画聚合而丢失 |
| C23 | 工作台与 MCP 使用不同实例 | 在接入检查阶段发现，不生成看似成功的项目/agent |
| C24 | 老数据、旧工具与发布包 | migration 幂等、旧权限不扩大、旧证据/版本可回查、新页面在包中 |

新增验证使用临时 DB + 真 HTTP MCP SDK 客户端 + 实际浏览器状态检查，先覆盖协议、接入和页面确定性行为；不用真实模型费用证明幂等、租约和消息路由。真实宿主判断/材料质量另在 D4 如实记录，不混成协议通过率。

## 13. 本轮应确认的设计结论

工作流中心是“一个目标、一间办公室、多个独立 agent”，用户先看得到人和分工，再按需展开权限与协议细节。工作服提供文件可见性的直观线索，材料清单和访问证据负责准确性。协作采用明确的通知、请求、委托、负责权转移与验收；所有状态来自持久回执或带来源的报告。所有 agent 的所有 MindPond 操作仅走 HTTP MCP。
