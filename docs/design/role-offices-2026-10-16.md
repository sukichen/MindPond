# 角色、会话与跨办公室协作

日期：2026-10-16。状态：下一版实施设计。本文的 `role_*`、申请审批和宿主继续执行协议尚未实现，不能作为现有 MCP 工具使用。现有 v2 接口继续按[当前说明](../collaboration-offices.md)运行。

## 1. 本次改变

协作的主体是一个长期角色人物。Codex、OpenCode、Claude Code 是承载它的宿主，不是人物的名字，也不决定它在办公室的职务。

```text
账户 → 宿主接入授权 → 聊天会话绑定 → 长期角色人物
                                   ├─ 研发办公室：开发职务
                                   ├─ 验收办公室：复现职务
                                   ├─ 角色收件箱、身份介绍、知识索引
                                   └─ 当前工作地点、实际运行状态
```

同一宿主的两个聊天可以分别承载“小栗”和“小麦”。小栗从研发办公室转到另一个任务办公室，roleId、介绍和个人工作积累保留。办公室职务、任务、文件访问条件和授权在新办公室重新确定。

**人物身份、临时职务、权限与运行状态是四件事。** 修改名字不增加权限，移动人物不迁移所有聊天内容，动画不能证明宿主正在执行。

## 2. 对象与约束

| 对象 | 作用 | 关键约束 |
|---|---|---|
| Account | 用户与数据所有权 | 跨账户授权保持独立 |
| Connector | 宿主的 HTTP MCP 接入 | 保存技术信息，不再作为人员目录 |
| RuntimeBinding | 一个可恢复的真实聊天/受限宿主实例与角色的绑定 | 由可信宿主身份或受限凭据约束，不靠模型声称的 sessionId |
| CharacterRole | 稳定人物：名字、介绍、专业方向、知识索引 | 稳定 roleId；用户编辑有 revision 和历史 |
| OfficeAssignment | 角色在一个办公室的职务和允许操作 | 与人物介绍分开；可撤销、有修订号 |
| RoleMailbox | 跟随人物的收件箱 | 读取不等于处理；可跨办公室收件 |
| Office / WorkItem / Round | 任务、责任、材料、验收 | 保留现有租约、版本、幂等、预算和证据约束 |

默认：一个真实聊天绑定一个角色；一个角色只有一个可写的活跃承载会话。接管需要用户明确批准并递增 bindingEpoch，旧会话的写入、任务租约和等待均失效。允许只读观察者，但不把多个会话自动合并为同一执行者。

角色可以参加多间办公室，只有一个当前主要工作地点；其它地点显示其分工和“当前在另一办公室”，不能画成多个同时工作的分身。不同任务仍可并行等待，但要由宿主能力与任务租约明确体现。

## 3. LLM 不持有 token 的接入边界

认证在 MCP 工具调用之前完成。宿主 HTTP MCP 客户端从其秘密存储读取 Bearer，MindPond 从传输认证得到 Account / Connector。LLM 只看见公开 roleId、bindingId、officeId 和当前能力。

不提供取 token 的工具；token 不进入工具参数/结果、申请材料、角色介绍、知识包、URL、聊天提示词、事件日志或导出模板。模型也不应通过 shell 读取认证文件或输出环境变量。

必须同时说明：变量引用能避免把秘密直接放入提示词，但如果模型的 shell 与宿主有相同的读取权限，变量/0600 文件不能构成秘密隔离。强隔离需要宿主秘密存储与工具进程之间的真实权限边界。

### 3.1 为什么不能仅靠 MCP 连接识别聊天

MCP transport session 不等于 harness chat session。宿主可能复用 MCP 连接，也可能在同一聊天中重连。`clientInfo.name = codex`、IP、工作目录、模型填写的 sessionId 都不足以证明当前聊天是谁。

因此提供两种明确标示的能力等级：

1. **通用 MCP 模式**：模型提交公开的上下文编号，用户审核人物和申请；用于正常协作中的显式身份选择。共享一个广泛凭据的其它聊天可能选择同一上下文，不能宣称逐聊天安全隔离。
2. **宿主绑定模式**：宿主在模型之外为每个真实 session 提供独立受限接入，或由可信宿主组件把真实 thread/session 绑定到运行身份。审批绑定的是这份运行身份。模型参数只能缩小权限。重连时用宿主保管的恢复凭据恢复，而不是拿公开 bindingId 取得权限。

UI 必须显示当前等级。未能获得可信逐会话标识的宿主，不允许展示“已验证独立会话”或自动挑选“最后使用的角色”。多个候选时返回 context_required。

### 3.2 文件夹方案可作为宿主启动配置，不能成为认证依据

建议允许用户准备一个独立的角色启动目录：

```text
role-workspace/
  .mindpond/identity.json  # 公开引用：instanceId、roleId、配置版本；没有秘密
  .codex/config.toml      # 原生 HTTP MCP 地址与秘密变量名；不含值
  .opencode/commands/     # 可选手动命令模板
```

该目录方便启动与恢复，不要求 agent 能访问 MindPond 本地文档。角色真身及审批状态始终以中心服务为准。复制目录、复制公开 roleId 或改介绍，都不能获得已有角色的身份。Git 中只允许公开模板。

一个文件夹内开多个聊天仍可能共用 MCP 配置，所以“不同文件夹”不是“不同 session”的通用替代品。强隔离的简单路径是每个角色一个独立受限宿主实例/启动配置；具体宿主支持真实逐 session 接入时，再共用实例。角色目录也不等于仓库副本；工作目录和文件互通必须分别申报。

### 3.3 用户实际需要做什么

这里的“宿主”是运行聊天、执行工具并建立 MCP 连接的程序：Codex 桌面应用、Codex CLI、OpenCode 等。MindPond 是它访问的服务；LLM 不负责保管连接凭据。

**正常的单用户多角色协作，应先提供无需修改宿主的显式上下文流程。** 不应把实现强身份隔离的要求变成使用角色的前置条件。共享本人凭据下的合作式上下文选择与互不信任用户之间的认证隔离，需要在页面上分别说明。

当前已有工具可这样使用：

1. 用户把中心 HTTP MCP 接入宿主，配置一次宿主读取的认证来源。Codex 的 `bearer_token_env_var` 是秘密变量的名称，LLM 不需要知道变量的值。配置文件本身不负责生成这个值。
2. 用户在当前 v2 页面给聊天 A、B 分别安排不同工位。
3. 聊天 A 调用 work_bootstrap，然后以用户指定的 assignmentId 调用 work_session_open；聊天 B 领取自己的另一个工位。
4. 两个聊天只保存各自公开的 workSessionId，并在协作/当前工作上下文的记忆调用中携带。它不是 token，不能单独绕过接入授权。
5. 上下文丢失后恢复明确的工作编号；不能根据全局“最近活跃”记录替另一个聊天选身份。

新角色协议实现后，步骤 2–3 变为“当前聊天通过 MCP 申请人物 → 用户在页面批准 → 当前聊天 role_sync 获得人物资料”，审批后再安排办公室。它不是当前已实现的操作。

公开绑定信息如需落盘，必须按聊天分开，例如 `.mindpond/sessions/<public-chat-id>.json`，其中只有 instanceId、roleId、bindingId 等引用。禁止使用一个所有聊天都覆盖的 `current-role.json`。复制这些文件不能成为获得权限的依据。只有 MCP 的客户端仍必须能使用显式上下文流程，不能把读本地文件作为必要步骤。

对具备自动会话标识的客户端，再减少模型携带编号的负担。例如 [OpenCode 新版 MCP 文档](https://dev.opencode.ai/v2/docs/mcp-servers/#context)说明，调用元数据中会附带 `_meta["ai.opencode/sessionID"]`。实施时应验证实际安装版本、直接工具/Code Mode、HTTP 传输与重连；不能据新版文档推断所有旧版本都会发送。MindPond 应从已认证客户端的传输元数据读取它，而非让模型在业务参数中自行填写。这个公开编号是关联信息，认证仍来自宿主凭据；需要防止同权限恶意客户端冒充时，还需受限接入或额外可信绑定。

截至本次文档核查，Codex 的公开 MCP 配置文档说明了 Bearer/headers 与项目配置，但未据此建立它向任意第三方 HTTP MCP 自动提供可信逐聊天标识的保证。先验收显式上下文模式；能实际证明其逐聊天元数据或受控运行端的，再启用自动绑定。不要要求用户设置一个静态 `SESSION_ID` 环境变量后，就宣称同一宿主中的所有聊天已自动区分。

## 4. 用户期望的申请与审核流程

前提：用户已把通用 HTTP MCP 服务接入宿主。尚未认证的模型不能先调用一个工具领取 token 来认证自己。

1. 当前聊天调用候选 `role_application_submit`，提出名称、介绍、专长、申请理由和公开宿主标签。工具只提交申请，不产生角色权限。
2. 服务端记录已经认证的 Account / Connector、绑定模式、可信 runtime（若有）、申请摘要及幂等键。LLM 填写的 harness 名称与目录标记为自报信息。
3. 前端“待审核”显示真实账户、绑定保证、拟建人物和申请时间。用户可修改后批准、拒绝或要求补充；审批需要 expectedRevision，并保留用户操作事件。
4. 批准后生成角色、配置可读知识范围、建立或等待确认 RuntimeBinding。只批准人物，不自动加入所有办公室，不自动授权后台运行。
5. 同一聊天调用候选 `role_sync`，得到审核结果和自己的介绍。若启用可信宿主继续组件，审核结果作为一个控制事件唤醒原聊天；否则页面明确“等待此聊天再次同步”。审批本身不能让已停止的 LLM 自发执行。
6. 用户在前端将角色安排进办公室。下一次同步得到职务、目标、验收条件、截止、预算和文件访问待确认事项。

申请丢失回复后重投同 key/同载荷返回同一申请；不同载荷冲突。重复批准只有一个角色。过期、撤销、拒绝的申请不能恢复权限。新 session 接管已有角色与新建角色是不同申请，不能冒用“申请重名”覆盖已有绑定。

## 5. 角色介绍和知识随人物移动

人物资料包含 `name / introduction / specialties / workingPreferences / avatar / profileRevision`。用户修改后发布 `role_profile_changed` 控制事件；每次 role_sync 和实质工作前返回新版完整简介或差量。模型确认读取后才推进其 seenProfileRevision。名称保持历史快照，历史消息不会被改名操作重新署名。

角色知识包先做成**用户授权的具名知识集合与索引**，复用已有 memory/domain/space，不另造一套不兼容的 domain。包括角色工作经验、手册摘要、来源、置信状态和 memory 引用。角色只能带走已获授权、适合长期保留的知识；办公室原始材料、会话私密内容和其它项目全文不会自动打包。

每次换办公室重新检查引用的可读权限和时效。目标角色没有源域权限时，只能通过明确发布的文本包传递必要内容；不能通过知识包引用绕过 ACL。修改名字/介绍不移动记忆归属；角色删除或停用也不静默删除历史证据。

Session 过程记忆继续按真实聊天/工作上下文隔离。长期角色积累需要普通 memory save/edit/feedback 流程，不能直接把全部 session 转为人物画像。

## 6. 角色收件箱与跨办公室通信

收件人是稳定 roleId，不是 Codex/账户名/某一次工位编号。消息信封包括：发送角色、接收角色、来源办公室/任务、目标办公室/任务（可选）、threadId、requestId、replyTo、类型、公开正文/材料引用、授权快照和序号。

允许的动作：通知、请求答复、提出任务交付、追问、补充材料、最终答复、撤回待接收交付。负责权转移仍需目标接受，不能由发消息直接改 owner。跨办公室委派先建立目标办公室的工作项/交付提议，双方任务通过显式链接关联；不跨办公室共享同一条可变任务记录。

由用户配置公司/协作组织的角色通讯权限和办公室之间的外发规则。获准通信不等于加入目标办公室，也不等于可读对方所有任务/记忆。接收者能读的是信封里正式发布的材料；私有材料引用不通则返回需要发布文本包，不把整段任务历史隐式附送。

请求的原发起角色移动办公室后，仍能收到原 requestId 的回复。办公室归档后可查看历史，但不接受新任务写入；未完成跨办公室请求需要显式关闭或转交。停用/删除目标角色返回不可达状态，不无限显示“正在等待”。

消息生命周期区分 queued、read、accepted、replied、resolved、declined、cancelled。普通通知可在明确读回执后归档；请求/任务文件应在完成答复或解决后离开待处理文件堆。看过预览不等于处理完。

## 7. 手动命令与自动继续是两条能力

### 7.1 手动入口

提供宿主安装包中的无秘密模板：查看收件箱、同步自己、申请角色、继续当前协作、停止自动接收。

- OpenCode：候选 `/mp-inbox`、`/mp-sync`、`/mp-join`、`/mp-continue`，使用其官方自定义 command 机制。
- Codex：提供对应 Skill，通过 `/skills` 选择，或使用宿主已支持的显式 Skill 引用。不承诺安装一个 MCP 就能增加任意原生 `/mp-inbox` slash command。
- MCP-only 客户端：直接调用 role_sync / role_receive；所有必要规则由 MCP tool descriptions / 结果给出，Skill 仅是快捷入口。

命令只帮助用户触发当前聊天的一轮；不能在没有用户输入或宿主调度的情况下自动唤醒已经结束的轮次。

### 7.2 自动继续

MindPond 保持无 LLM 的中心服务。可选、薄的宿主继续组件在模型之外工作：

```text
角色提交交付并进入 waiting
  → 宿主组件用 HTTP MCP 长等角色收件箱，不循环调用 LLM
  → 收到精确 requestId / roundId 的事件
  → 验证绑定 epoch、运行授权、预算和目标 session 状态
  → 对原 session 开启下一轮，提示它通过 MCP 读取事件
  → 模型读取完整材料并继续任务
```

Codex 可研究并验收 App Server 的 thread/resume、turn/start；OpenCode 可研究并验收 SDK 的 session.prompt / session.command 与 session 状态事件。它们是宿主集成能力，不能宣称仅凭标准 MCP 即可远程控制任意已有桌面聊天。必须拥有实际运行端点及该 session 的合法控制权；不创建“同名新聊天”假冒恢复原聊天。

用户必须按角色会话启用持续协作，限定哪些办公室/请求可以唤醒、有效期、轮数/费用预算。人工停止、审批等待和授权问题优先于自动继续，不能被新消息覆盖。宿主不支持时显示“已送达，等待手动继续”，不能用打字动画伪装。

每个 session 最多一轮在执行，批量合并同时到达的事件。wakeId + bindingEpoch + 宿主 runId 做持久投递与去重；宿主忙时排队。启动下一轮的应答丢失时先查询真实 run 状态，无法确认则标记 delivery_unknown 并停止重复触发，不能声称跨两个系统严格 exactly-once。恢复已有记录、续传游标、取消和退避均不依赖模型记住 token。

跨角色消息是工作材料，不因唤醒而变为用户的高优先级指令；自动继续不扩大执行/文件/网络权限。

## 8. 办公室界面

主入口名称改为“协作办公室”。新版顶层导航为：办公室、角色、待审核、消息、接入设置。宿主/凭据移到高级接入页，人员目录以角色人物为主。

角色卡片显示名字、介绍、当前宿主、当前工作地点、绑定保证、待处理数量和最后真实活动时间。用户可以改名、改介绍、调整外观、移动办公室、安排职务、暂停或撤销承载会话。

办公室采用实际平面场景：地板、桌子、椅子、显示器、文件堆、门、公共休息位置；可爱的原创小人物负责空间表达。人物/桌子可点开，始终能切换到清楚的列表视图。移动端以当前办公室与少量可见桌位为主，详情独立抽屉；不能把整个桌面缩小到字无法阅读。

| 已证实业务状态 | 人物表现 | 信息要求 |
|---|---|---|
| 可达且没有正在执行的工作 | 打盹、喝水或玩耍 | “空闲/休息”，不暗示有执行进度 |
| 宿主确认正在执行且有有效任务 | 敲键盘/忙碌 | 当前动作、公开原因、对应任务 |
| 等待同办公室角色精确回复 | 移到目标桌边休息 | 等谁、请求摘要、等待时长 |
| 等待其它办公室 | 移到门口/跨部门交接点 | 目标办公室与角色，可跳转 |
| 有待处理消息 | 桌上出现纸张/文件夹 | 文件堆与待处理总数一致，附数字 |
| 宿主断开/很久无可达证明 | 静止、灰标或空椅 | “离线/状态未知”，不能画成正常休息 |
| 条件不足/授权等待 | 停在桌边，有明确标记 | 具体阻塞与需要谁处理 |

文件堆数量上限可视化 12 份，旁边显示实际数字；读过但尚未处理的请求仍保留文件。完整处理才减少。只动画新事件，历史重放直接还原终态，不播放几百次走路。角色改介绍产生一个系统文件，读后刷新人物介绍。

多个等待对象选一个主要目标位置，其余用数量显示；不能同时画成在多张桌旁。文件共享组用外套/徽章表达，但始终标记自报、观察时间及版本；不得把同色衣服等同于文件访问证明。

状态、任务、消息来自后端事件及宿主运行回执。减少动态效果、后台页暂停、低性能静态模式、键盘操作、颜色之外的标签、列表替代视图均是第一版验收项。第一版可用 DOM/CSS transform 实现，不要求独立显卡，不把装饰动画与业务状态耦合。

## 9. 候选 MCP 接口（规划名）

尽量保留少量易发现的入口，并在每次结果中附最小身份徽标与下一步：

| 入口 | 能力 |
|---|---|
| role_application | submit/status/cancel；新人物与接管已有角色分开 |
| role_sync | 自己、资料修订、审批、办公室分工、知识目录和待处理摘要 |
| role_receive | 有界等待/分页收件，支持精确请求，返回安全恢复参数 |
| role_exchange | 定向通知/请求/答复/明确处理回执 |
| office_get / work_office_item / work_material | 复用现有办公室任务、材料和版本验收流程 |

用户审批、角色改名/介绍、办公室安排、会话接管和外发授权仅在用户管理控制面，不作为 agent 可自行提权的工具。API 的 mutation 统一幂等键、expectedRevision、bindingEpoch 和结构化错误。

最小常驻提示词说明：先 role_sync；身份以服务端为准；保存必要公开上下文编号；每次实质工作检查角色介绍/分工修订；精确等待；超时是 pending；通过 MCP 获取指南；不读取 token。

## 10. 代码改造与迁移顺序

1. **角色与审批数据层**：新增独立模块，不继续扩大 OfficeStore。候选表：roles、role_profile_revisions、role_applications、runtime_role_bindings、role_knowledge_refs、role_mailbox、role_delivery_receipts。复用 ConnectionCoordinator 与 audit，先测试迁移、审批原子性和旧绑定 fencing。
2. **MCP 可信身份**：扩展 TrustedCallContext 与 network gateway。内部保留 connector/credential，但不以 agentId 作为业务收件人。bootstrap/sync 不从全局最后活跃角色推断身份。MCP-only 模式也必须能申请/读规则，不依赖本地文档。
3. **稳定角色消息**：收件箱按 roleId；officeId 作为来源/目的上下文。保留定向请求、文本包、两阶段负责权转移和精确验收。加入跨办公室外发/读取校验。
4. **职务映射**：旧 office_seats 逐步指向 roleId；原 role 字段改为 duty。先由用户显式映射旧工位到人物，不能只按 agentId 合并：同一 Codex 的两个工位可能本来就是两个人。
5. **用户控制面与界面**：先做角色目录、待审核、调配、介绍变更、消息，再做房间场景与人物状态；任何动画必须能从事件快照完整恢复。
6. **手动命令包**：分别验证 OpenCode commands 和 Codex Skill；不向宿主秘密路径写入公开资料。
7. **可选宿主继续组件**：由用户选定第一批宿主；不绕过已有权限、人工停止或会话归属。MindPond 仍只通过 HTTP MCP 与 agent/组件交互。
8. **验收后默认切换**：旧 v1/v2 工具与历史保留只读/兼容入口，明确迁移状态；不能只把 agent 字样替换为角色却继续使用旧身份边界。

当前入口对应：src/core/office.ts、office-tools.ts、trust.ts、integrations/network-server.ts、office-workbench.ts、mcp-service.ts、web/office.*。角色、路由投递与宿主继续应分成独立模块，避免办公室展示层负责认证或直接调模型。

## 11. 必须覆盖的反例

- 一个 Codex 两个真实聊天共用目录/连接；另一个聊天重连；上下文压缩；复制公开角色文件；切换机器；session fork。
- 用户批准申请时原连接已断；重复批准；拒绝后旧请求重放；角色重名；接管后旧会话继续提交；撤权时有悬挂等待。
- 角色调办公室时仍有租约、未验收轮次和待回复请求：先处理责任/解绑，原信封与历史署名保留。
- 修改介绍后模型尚未同步；只改名字不改权限；知识引用在新办公室不可读；删除来源记忆；多个来源有相互矛盾的结论。
- 跨部门路径/文件不可见；文本包完整性；材料私有引用绕权；对方无通信权限；目标角色停用；办公室归档。
- 回复先于等待；同一时刻多个消息；宿主忙；用户刚停止；唤醒应答丢失；重启后恢复；连接正常但模型不可用；预算耗尽。
- 只读未处理的文件不能消失；待处理数大于可视堆叠上限；目标角色搬走；多个等待对象；旧事件回放；手机操作；减少动态效果。
- 两个不同模型均通过标准 HTTP MCP 完成“申请→用户批准→同步→跨办公室交付→最终回复”，再分别验收真实宿主继续，禁止把 SDK 脚本通过当作真人宿主已经支持。

## 12. 官方能力依据与边界

- [Codex MCP](https://learn.chatgpt.com/docs/extend/mcp)：项目级配置、宿主附加 Bearer 与环境变量/headers 配置。文档未证明任意共享连接天然带可信逐聊天 ID。
- [Codex developer commands](https://learn.chatgpt.com/docs/developer-commands?surface=cli)：/skills 可选择 Skill；不据此承诺任意 MCP server 可新增原生 slash command。
- [Codex App Server](https://learn.chatgpt.com/docs/app-server)：对受控 thread 恢复和启动新 turn 的集成能力；不等于任何第三方程序均能控制正在使用的桌面聊天。
- [OpenCode commands](https://docs.opencode.ai/docs/commands/)：自定义命令文件和配置模板。
- [OpenCode SDK](https://docs.opencode.ai/docs/sdk/) 与 [plugins](https://docs.opencode.ai/docs/plugins/)：定向 session 请求、事件与集成接口；具体宿主版本与权限仍需端到端验证。
